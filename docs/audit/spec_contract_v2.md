# Контракт v2 оценки звонка (ИИ-Аудит)

Основа: разведка 2026-11-04. Настоящих клиентов нет, поэтому оценку можно менять без отметки о смене методики. Прод на момент написания: приложение `e7a2c05`, n8n `763533c8`. Итоги пилота: раздел 9.

## 1. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Что может быть «неприменимо» (н/п) | Только CR5 «Дорого», CR6 «Подумаю», CR13 «Маржа» | Ситуацию создаёт клиент, менеджер не может уйти от оценки, замолчав тему |
| Этапные критерии (ЛПР, боли, кейсы, дожим, фиксация) | Всегда 0 или 1. По длине звонка не отключаем | Иначе рано сдавшийся менеджер получает поблажку |
| Шкала | Остаётся 13, балл приводится: `round(13 × пройдено / применимо)` | Применимо всегда 10–13, множитель максимум 1.3. Пороги 9/6, Пульс, стендап, поля CRM и задача РОПу не меняются |
| Что видит человек | Таблица: `8/13`. Карточка: «Пройдено 6 из 10 применимых» | Балл сравним между звонками, а расчёт виден |
| Цитаты | Причина у каждого критерия, цитата где есть что цитировать | За «0» часто нечего цитировать: менеджер как раз этого не сделал |
| Проверка цитаты | Код проверяет, что цитата есть в транскрипте, иначе убирает её | Выдуманная цитата хуже её отсутствия |
| CR11 «Слушание клиента» | Считает код: доля слов клиента ≥ 30% | ИИ ставит 1 почти всегда. При 40% проходят 3 из 16, при 30% 8 из 16: критерий начинает различать звонки, монолог менеджера (9–22%) не проходит. Пересмотреть на звонках настоящих клиентов |
| Модель | Записывать `modelVersion` у каждого звонка | Цепочка из 4 моделей: иначе смена модели неотличима от изменения работы менеджера |
| `call_type`, суть звонка | Передавать в ЛК | ИИ уже их возвращает, они теряются |
| Версия оценки | `audit_version: 2` у каждого звонка | Нужна для сравнения периодов и будущих изменений промта |
| `call_worker` | Заморожен, не трогаем | Решение пользователя |

## 2. Изменения промта (все 4 копии: 17, 17a, 17b, 17c)

Готовый текст: `scripts/pilot/prompts/B_v2.txt`, отличия от боевого `A_current.txt`:
- формат транскрипта: каждая реплика с новой строки, только «Менеджер:» и «Клиент:»;
- `null` только для `cr5`, `cr6`, `cr13` с условиями;
- `evidence`: `why` и `quote` у каждого критерия;
- `ended_by`, `reached_decision_maker`: пока только копим, в оценку не идут.

В `generationConfig` добавить `responseSchema` (тип OBJECT, все поля; `cr5`, `cr6`, `cr13` с `nullable: true`). `maxOutputTokens` НЕ ставить: в него входит «мышление», в пробе 15 360 токенов из 16 000 ушло на него и ответ оборвался.

## 3. Узел 18

- Ответ-массив `[{...}]` развернуть в объект до чтения полей. Пустой транскрипт это сбой анализа, а не недозвон (боевая ошибка, раздел 9). `parseTrimmed` остаётся.
- `cr5`, `cr6`, `cr13`: null сохраняется. Остальные: всё, что не 1, это 0, как сейчас.
- `passed` = сумма, `applicable` = 13 минус число null, `total_score` = `Math.round(13 * passed / applicable)`.
- Недозвон и сбой: как сейчас (оценки нет).
- CR11 считает код: доля слов клиента ≥ 30%, разбор регулярным выражением `(Менеджер|Клиент( \d+)?)\s*:`, а не по строкам. Нет подписей: значение ИИ.
- `evidence`: обрезать длины, проверить цитату (без регистра, знаков препинания и лишних пробелов), не найдена: `quote = ""`, счётчик `evidence_unverified`.
- Заметка CRM: при `applicable < 13` дописать «(оценено N из 13)». Бейдж и пороги прежние.
- Новые поля наружу: `passed`, `applicable`, `evidence`, `ended_by`, `reached_decision_maker`, `audit_model` (`item.json.modelVersion`), `audit_version: 2`, `summary` (`amo_short_summary`), `audio_url` (из `source`).
- Заодно: `manager_skill_cluster` на порогах 9/6; убрать выдуманный `D-100+i`.

## 4. API и хранение

- 18b и `CallIngestPayload`: `audio_url`, `call_type`, `summary`, `evidence`, `passed`, `applicable`, `ended_by`, `reached_decision_maker`, `audit_model`, `audit_version`. Всё в `scorecard_criteria` (JSON), миграция не нужна. `audio_url` дополнительно в колонку `audio_s3_url`.
- `_format_db_call` отдаёт эти поля и `has_audio`. Саму ссылку фронт не получает.
- `read_scorecard` не меняется: явный `score` уже имеет приоритет, null в `cr` допустим.
- Google Sheets: новые поля не пишем. Узел 19 получит приведённый балл и пустые ячейки для null, чтение это уже понимает.
- `GET /calls/{id}/audio`: проверка входа и клиента, запись из нашего хранилища отдаётся файлом, внешняя ссылка проксируется с `Range` и без токенов CRM, защита от SSRF (только https, только публичные адреса). Нет записи: 404, плеер скрыт. Для Битрикса ссылку получать заново по `RECORD_FILE_ID`, если сохранённая истекла (отдельный шаг).

## 5. Интерфейс (карточка звонка, `AuditPage`, `CallDetailsDrawer`)

- Шапка: балл, затем «Пройдено 6 из 10 применимых», если есть н/п.
- Плеер: уже есть, подключить к `/calls/{id}/audio`.
- «Суть звонка» перед замечаниями.
- Критерий: 0, 1 или «н/п» серым. По клику раскрывается причина и цитата. Образец: `MethodologyXRayDrawer`.
- Тепловая карта и радар: логика уже верная (`criterionRates` пропускает null). Подсказка ячейки показывает, по скольким звонкам посчитан процент.
- `criteria.ts`: описания CR5, CR6, CR13 дополнить условием применимости, в CR11 указать 30%.

## 8. Не входит

- Этапные критерии как н/п: решаем по данным `ended_by` и `reached_decision_maker`.
- «Оспорить»: следующий пакет. Принцип: менеджер отмечает одним кликом, РОП решает одним кликом, без ответа остаётся оценка ИИ.
- Сравнение периодов: после этого контракта.
- Загрузка транскрипта при открытии карточки: вместе с динамикой.
- Методология (старая нумерация, синтетические данные): отдельный этап.

Разметка сделана по выдержкам с широким набором слов из полных транскриптов, пользователем не проверялась.

- A ставит 1 при отсутствии ситуации: «Дорого» 7 из 14, «Маржа» 7 из 14. B их убирает, поэтому B строже: средний 6.07 → 5.71, 4 вердикта из 14 вниз (норма→срыв 3, эталон→норма 1).

- Стоимость B: выход +46%, «мышление» +41%, задержка 23 с против 18 (медиана).
- Сбои инфраструктуры одинаковы для A и B: 503, 524, затем 429.

Боевые проблемы:
- Ложный недозвон ПОДТВЕРЖДЁН на одной записи: звонок `…1_f46a` хранится как недозвон с пустым транскриптом, повторный прогон дал разговор на 1298 слов, тип qualification, 6/13. Причина пустоты не доказана: 1 из 20 ответов A пришёл массивом `[{...}]`, а узел 18 в этом случае читает пустые поля и решает «недозвон». Вторая подозрительная запись `…3_bb14` оказалась настоящим недозвоном: повтор дал те же 6 слов и «Недозвон».
- `gemini-3.5-flash` отвечает как `gemini-3.6-flash` (`modelVersion`): модель под именем меняется без предупреждения, поэтому `audit_model` нужно записывать.

Прокси Gemini (код воркера Cloudflare, прочитан 2026-11-04):
- Ротация работает: при 429 перебирает все ключи. Значит, 429 на выходе = все ключи исчерпаны на этой модели.
- Лимиты бесплатного тарифа считаются на проект Google, а не на ключ (по документации, как я её помню, проверить). Ключи из одного проекта ротация не складывает.
- Воркер открыт: запрос без параметра `key` получает ключи из пула, проверки доступа нет (по коду, не проверялось запуском).
- Ключи записаны в коде воркера открытым текстом, `GEMINI_PROXY_KEY` на сервере это один из ключей Google, он же в URL узлов n8n. Нужно: новые ключи, хранить в секретах воркера, в воркере проверять отдельный секрет доступа.
- Для клиентов нужен платный ключ: лимиты и условия обработки данных.

Решения по ходу:
- Запись в amoCRM на домене amoCRM может требовать токен (узел 15 для неё его добавляет). Прокси токен не отправляет, поэтому такая запись покажет «Запись недоступна». Если это окажется частым случаем на настоящих клиентах: брать запись на сервере с токеном клиента, только на домен его CRM.
- Известный зазор SSRF: имя проверяется и потом открывается заново (DNS rebinding). Ссылку пишет наш n8n, не пользователь, закрепление соединения не оправдано.
- Старые строки без `has_audio`: плеер не показывается, вместо мёртвого `<audio>`.
- Карточка сделки (`DealDetailsDrawer`) считает балл звонка как `{overall_score}%` (шкала 13 показывается как процент) и читает критерии своим разбором: отдельная находка, здесь тронуты только «н/п» и плеер.

Осталось: пилот B на 16 звонках после появления квоты, затем патч промта в 4 копиях узла 17 (`B_v2.txt` + `responseSchema`), деплой и один живой звонок.

Правки после ревью (Opus, 10 находок): плеер не включает запись предыдущего звонка; карточка сделки не рисует крестики у недозвона; `null` вне CR5/6/13 отклоняется при приёме (422), без балла он приводится к 13; вебхуки и воркер больше не выбрасывают оценку с «н/п»; `has_audio` только для ссылки, которую плеер может сыграть (https, порт 443, или наше хранилище); битая ссылка = 404, а не 500; сессия БД закрывается до потока записи; патч промта пишет `node_check.js`; разбор пилота считает как узел 18 (пропуск поля = 0) и только вариант B.

Известное ограничение: запись скачивается целиком перед проигрыванием (спиннер без отмены; перемотка средствами браузера по уже загруженному). `Range` на сервере заложен, но кабинетом не используется. Потоковый вариант (`<audio src>` с cookie `access_token`) требует проверки на проде: отдельный шаг.
